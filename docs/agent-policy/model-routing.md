# 위험도 기반 모델 라우팅 및 검증 정책

이 문서는 **AI Learning Studio** 프로젝트에서 작업의 위험도에 따라 AI 모델(구현 모델 및 검증 모델)의 적합성을 사전에 점검하고, 실행 후 증거 기반으로 검증하는 세부 운영 정책을 정의합니다.

---

## 1. 위험도 3단계 분류 기준

모든 구현·수정 요청은 시작 전에 아래 기준에 따라 위험도를 엄격히 분류합니다.

| 위험도 등급 | 대상 및 작업 범위 | 사전 분석 요건 | 사후 검증 요건 |
| :--- | :--- | :--- | :--- |
| **고위험 (High)** | · 아키텍처, 데이터 흐름 또는 빌드 계약 변경<br>· 여러 모듈·컴포넌트에 걸친 변경<br>· API, 라우팅, 데이터 스키마(JSON/Frontmatter) 변경<br>· 공통 템플릿(`templates/base.html`), 공통 CSS(`site.css`), 공통 렌더러 또는 전체 페이지 생성 로직 변경<br>· 보안, 성능, 데이터 무결성, 배포 파이프라인 변경<br>· 원인·해결책의 불확실성이 높은 난제 버그 | **상위 추론 모델 사전 분석 필수** | **상위 검증 모델 사후 검증 필수** |
| **중간 위험 (Medium)** | · 단일 페이지 전용 렌더링 변경 및 개별 컴포넌트 로직 수정<br>· 단일 모듈 내의 기능 추가 및 수정<br>· 동작에 영향을 주는 비즈니스 로직 변경 | 상위 모델 사전 분석 선택 (구현 모델 자체 분석 가능) | **상위 검증 모델 사후 검증 필수** |
| **저위험 (Low)** | · 읽기 전용 코드/문서 조사 및 설명<br>· 단순 오탈자, 주석, 일반 문서 표현 수정 (단, `AGENTS.md`, `docs/agent-policy/`, `agent-logs/` 제외)<br>· 실제 동작·생성 결과에 영향을 주지 않는 순수 서식 정돈 | 사전 점검 보고 생략 가능 | **상위 검증 생략 가능** |

### ⚠️ 위험도 판정 시 주의사항 (승격 및 예외 규정)
1. **마크다운 수정의 위험도 판정**:
   - 단순 포맷 정돈이라도 프롬프트 내용, Frontmatter 메타데이터, 페이지 레지스트리, 정적 HTML 생성 결과에 영향을 주면 **실질적 변경(중간 위험 또는 고위험)**으로 간주합니다.
2. **템플릿 수정의 위험도 승격**:
   - 단일 페이지 전용 변경은 중간 위험으로 분류할 수 있으나, 공통 템플릿, 공통 스타일, 공통 렌더러로 범위가 확장되면 **즉시 고위험으로 승격**합니다.
3. **운영 계약 및 정책 문서의 위험도**:
   - `AGENTS.md`, `docs/agent-policy/`, `agent-logs/` 수정은 일반 문서 수정이 아니며, 사전 계획 보고 및 사용자 승인이 필수인 최소 중간 위험 이상의 작업으로 분류합니다.
4. **위험도 우선 원칙**:
   - 변경 규모(diff 줄 수)가 작더라도 핵심 경로, 데이터 무결성, 공개 계약에 영향을 미치면 고위험으로 판단합니다.

## 2. 작업 전 모델 적합성 점검 (사전 게이트)

- 구현 모델과 검증 모델의 권장 수준을 작업 착수 전에 먼저 판단합니다.
- 모델 수준(Tier)은 특정 모델명이 아닌 기능적 추론 역량(Capability)을 기준으로 정의합니다:
  - **상위 추론형 (High-Reasoning Tier)**: 심층 하이브리드 추론, 복합 상태 추적, 전체 아키텍처 합성 역량을 갖춘 모델.
  - **일반형 / 비용 효율형 (Standard / Cost-Efficient Tier)**: 국소 코드 수정, 단순 서식 치환, 빠른 응답에 최적화된 모델.
- 모델 적합성 판단을 위한 최소한의 읽기 전용 조사는 수행할 수 있으나, 적합성 판단 전에는 파일을 절대 수정하지 않습니다.
- **고위험 작업 차단**: 고위험 작업은 상위 추론 모델의 사전 분석 없이 실질적인 수정을 시작하지 않습니다.
- 현재 선택된 모델이 요구사항에 비해 낮다고 판단되면 파일 수정 전에 아래 양식으로 선보고하고 지시를 대기합니다:

```text
[모델 적합성 점검]
- 작업 위험도: 높음 / 중간 / 낮음
- 현재 모델: (현재 선택된 모델 또는 모델 등급)
- 권장 구현 모델 수준: 비용 효율형 / 일반형 / 상위 추론형
- 권장 검증 모델 수준: 일반 검증형 / 상위 검증형
- 권장 이유: (예: 공통 CSS 및 다중 모듈 렌더러 계약 영향 큼)
- 낮은 모델로 진행할 때 위험: (예: 전체 페이지 레이아웃 깨짐 및 빌드 실패 가능성)
- 권장 선택지:
  1) 상위 모델로 전환하여 분석·구현·검증 진행 (권장)
  2) 현재 모델로 읽기 전용 사전 조사 또는 PoC 분석만 수행
  3) 현재 모델로 진행하되, 실질적인 수정 전 사용자 승인 획득 (Override)
```

- **PoC 격리 원칙**: 선택지 2(사전 조사·PoC 결과)는 참고 자료로만 취급하며, 상위 모델 검토나 사용자 승인 없이 최종 구현·배포에 사용하지 않습니다.

## 3. 검증 독립성 및 Fallback / Override 처리 정책

### 3.1 검증 모드 및 독립성 기준
자기 승인 편향(Self-Approval Bias)을 차단하고 무결성을 유지하기 위해 검증 모드를 명확히 분리합니다:
1. **독립 상위 검증 (Independent Higher-Tier Verification)**:
   - 구현 세션과 분리된 별도 task, 서브에이전트 또는 fresh session에서 수행 (동일 task/세션 내의 후속 턴은 독립 세션으로 인정하지 않음).
   - 상위 추론/검증 역량을 갖춘 모델에 의해 수행되며, 공식 `Independent Higher-Tier PASS` 판정 부여.
2. **단일 세션 보상 검증 (Self Compensatory Verification)**:
   - 동일 구현 세션 내에서 도구 실행(빌드, 테스트, 스크린샷, diff)을 통해 자체 확인.
   - `Self Compensatory PASS` 판정 부여.
   - **절대 규칙**: 보상 검증 결과는 기술적으로 정상 통과일지라도 사용자 Override 하에서의 국소 도구 검증 결과이며, 고위험 작업의 공식 "독립 상위 검증 PASS"로 사칭하거나 허위 보고하는 것을 엄격히 금지합니다. 사용자의 명시적 Override 없는 자체 보상 검증은 고위험 작업의 최종 완료 승인과 동일하지 않습니다.

### 3.2 상위 모델 부재 시 Fallback 및 Override 처리 정책
1. **원칙적 착수 금지**:
   - 자동 모델 전환(handoff)을 지원하지 않는 단일 세션 환경에서 상위 모델을 호출할 수 없는 고위험 작업은 사용자에게 제한 사항과 대체 검증 방법을 보고하고, **사용자의 명시적 지시(Override) 전에는 실질적인 수정을 시작하지 않습니다.**
2. **Override 기록 및 보완 검증 의무**:
   - 사용자가 고위험 작업의 Override를 명시적으로 승인한 경우, **Override 사실과 사유를 작업 진행 로그(`progress-log.md`)에 명확히 기록**합니다.
   - Override 작업은 가능한 범위에서 테스트(`pytest`), 정적 빌드(`build.py`), 런타임/브라우저 확인 및 엄격한 diff 대조를 수행합니다.
   - 상위 검증을 수행하지 못한 작업은 "독립 상위 검증 완료"로 허위 보고하지 않으며, **"단일 세션 보상 검증 완료 (Self Compensatory)"**로 투명하게 기재합니다.

## 4. 검증 모델의 권한 및 책임

검증 모델은 주관적 추측을 배제하고 객관적인 실행 증거를 바탕으로 작업 완료 여부를 판단합니다.

- **금지 권한**:
  - 소스 코드, 설정 파일, 마크다운 콘텐츠 수정
  - Git 커밋, 푸시, 브랜치 조작 등 형상 변경
  - 외부 데이터 쓰기 및 비가역적 파괴 명령 실행
- **허용 권한**:
  - `git diff` 및 변경 내역 조회
  - 시스템 및 에이전트 작업 로그 조회
  - 테스트(`pytest`), 정적 빌드(`python3 scripts/build.py`), 프롬프트 감사(`audit_prompts.py`) 명령 실행
  - 브라우저 서브에이전트 실행을 통한 런타임 렌더링 및 스크린샷 교차 검증
- **임시 산출물 격리**:
  - 검증 명령 실행 중 생성되는 임시 산출물은 사전에 허용된 출력 경로(`dist/`, `outputs/`, `agent-logs/`)에만 생성해야 하며, 소스 코드 및 Git 상태를 오염시키지 않아야 합니다.

## 5. 검증 결과 보고 및 재검증 루프 (Verification Loop)

검증 완료 시 아래 표준 형식으로 보고합니다:

```text
[검증 결과]
- 상태: PASS / FAIL / BLOCKED
- 검증 모드: 독립 상위 검증 (Independent Higher-Tier) / 단일 세션 보상 검증 (Self Compensatory)
- 구현 Task/Session ID: (Task ID 또는 세션명)
- 검증 Task/Session ID: (Task ID 또는 세션명)
- 작업 트리 상태 / Ref: (Git commit SHA 또는 작업 트리 clean/dirty 상태)
- 확인 범위: (확인한 파일 목록 및 diff 요약)
- 실행 검증 증적:
  · 빌드: (python3 scripts/build.py 실행 결과 및 종료 코드)
  · 테스트/감사: (pytest 또는 audit_prompts.py 실행 결과)
  · 화면/렌더링: (브라우저 스크린샷 및 UI 렌더링 확인 결과)
- 발견 문제: (없음 또는 발견된 버그/사이드 이펙트)
- 심각도: 없음 / 경미 / 치명적
- 권장 조치: (완료 선언 또는 수정 지시)
- 재검증 필요 여부: (Y / N)
```

### 🔄 재검증 루프 (Failure Feedback Loop)
- 검증 상태가 `FAIL` 또는 `BLOCKED`인 경우:
  1. **문제 리포트**: 검증 모델이 실패 로그와 구체적인 결함 원인을 보고
  2. **수정 작업**: 구현 모델이 지적된 결함 부분을 수술적으로 수정
  3. **재실행**: 관련 테스트 및 빌드 명령 재실행
  4. **상위 재검증**: 검증 모델이 수정 diff와 실행 결과를 재검증하여 `PASS`를 확인할 때까지 반복
- 모든 결함이 해결되어 최종 `PASS` 판정을 받기 전까지는 작업을 완료로 처리하지 않습니다.

## 6. 임의 개선 방지 및 스코프 잠금 (No Speculative Polish & Scope Lock)

고추론 모델(Codex, Sol, Luna, Terra 계열 등)의 과도한 자의적 개선 시도(Over-Helpfulness)로 인해 프로젝트 아키텍처가 훼손되거나 무한 수정 루프에 빠지는 것을 방지하기 위해 다음 원칙을 절대 강제합니다.

### 6.1 임의 개선의 결함화 (No Speculative Polish)
1. **요청 외 변경 엄단**: 사용자가 명시적으로 요구한 파일/함수/라인 외의 코드를 '더 깔끔하게' 또는 '최적화'하기 위해 임의로 리팩토링하는 행위는 품질 향상이 아닌 **'승인 없는 스코프 위반 결함(Defect)'**으로 규정합니다.
2. **레거시 및 비효율성 존중**: 주변 코드에서 비효율성, 레거시 패턴, 미사용 변수, 타입 힌트 누락 등을 발견하더라도 사용자의 명시적 지시가 없다면 절대로 임의 수정하지 않습니다.
3. **최소 차분 최우선 (Surgical Priority)**: '더 완벽한 코드'보다 '요청된 최소 범위만 정확히 변경된 코드(Minimal Diff)'를 절대적 기준으로 삼습니다.

### 6.2 검증 모델의 이진 판정(Binary Pass/Fail) 강제
검증/리뷰 모델은 주관적 코드 개선안을 쏟아내며 수정 루프를 유발하지 않아야 하며, 오직 다음 3가지 객관적 기준에 대해서만 이진(Yes/No)으로 판정합니다:
1. **요구사항 구현 여부**: 사용자가 요청한 핵심 기능 및 변경사항이 정확히 반영되었는가? (Yes/No)
2. **회귀 및 빌드 무결성**: 테스트 스위트(`pytest`)와 정적 빌드(`build.py`)가 오류 없이 통과(Exit code 0)하는가? (Yes/No)
3. **무단 변경 부재**: 요청받지 않은 외부 파일이나 핵심 아키텍처를 임의 수정한 흔적이 없는가? (Yes/No)

### 6.3 비차단 개선 의견(Non-blocking Suggestions)의 격리
- 검증 과정에서 도출된 추가적인 리팩토링 제안, 스타일 통일, 성능 개선 아이디어는 **이번 작업의 `FAIL` 사유가 될 수 없습니다.**
- 이러한 의견은 코드 수정 루프로 환류하지 않고, 보고서의 **`[차기 참고 메모]`**로만 격리 기록합니다.

### 6.4 완료 정의(Definition of Done) 및 즉시 턴 종료
- 3대 이진 판정 기준을 모두 통과하면 모델은 더 이상의 자의적 탐색이나 추가 수정을 즉시 중단하고, 최종 요약 보고를 제출한 뒤 도구 호출을 종료(Stop Calling Tools)합니다.
